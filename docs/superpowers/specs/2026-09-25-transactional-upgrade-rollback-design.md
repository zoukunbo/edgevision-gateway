# Edge Gateway Lite 事务化升级与自动回滚设计

## 1. 目标

将当前“安装、重启、健康检查”流程扩展为可提交、可回滚的升级事务。
只有当安全检查全部通过、运行版本低于候选版本，且候选服务通过健康检查时，
本次升级才提交成功。

候选版本失败时，系统必须先停止候选进程，再恢复旧程序；数据库仅在候选版本
实际改变过数据库文件集合时恢复。最终必须查询实际运行版本并验证旧服务。

## 2. 非目标

- 本次不引入 A/B 分区、双版本长期共存或 `current` 符号链接。
- 不修改 SQLite schema、MQTT 协议、systemd 服务用户或设备权限。
- 不把串口不存在等环境错误伪装成升级成功。
- 不保留多代历史备份，只保留最近一次升级前备份。

## 3. 总体架构

新增 `upgrade-board.sh` 作为升级事务协调器。它负责：

1. 校验候选包和版本关系。
2. 检查当前服务和数据库是否具备安全升级条件。
3. 停止旧服务，建立完整备份。
4. 调用“只安装、不启动”的安装步骤。
5. 启动并验证候选版本。
6. 成功时提交，失败时按顺序回滚。

现有 `install-board.sh` 中的文件预检查、校验和复制逻辑将拆成可复用的安装单元。
事务协调器控制停止、启动、健康检查和回滚，避免安装函数在中途自行改变服务状态。

## 4. 状态流程

```text
PRECHECK
  ├─ 失败 → precheck_failed，不停止旧服务
  ↓
STOP_OLD
  ↓
BACKUP_OLD
  ├─ 失败 → START_OLD → VERIFY_OLD
  ↓
INSTALL_CANDIDATE
  ↓
START_CANDIDATE
  ↓
VERIFY_CANDIDATE
  ├─ 成功 → COMMIT → upgrade_committed
  └─ 失败 → STOP_CANDIDATE
                 → COMPARE_DATABASE
                 → RESTORE_DATABASE_IF_CHANGED
                 → RESTORE_OLD_PROGRAM
                 → START_OLD
                 → VERIFY_OLD
```

任何备份失败都必须发生在候选版本启动之前。此时不安装、不启动候选版本，
而是重新启动并验证原服务。

## 5. 升级前安全检查

进入 `STOP_OLD` 前必须同时满足：

- 发布包 `SHA256SUMS` 全部通过。
- `gateway`、`gatewayctl` 和必需部署脚本存在且权限正确。
- 当前服务能查询到非空、格式正确的运行版本。
- 候选程序版本非空且格式正确。
- 必须满足 `running_version < candidate_version`。
- 当前服务健康，不存在已知的串口、GPIO 或数据库环境错误。
- 数据库存在，且 `PRAGMA integrity_check` 返回 `ok`。
- 备份位置有足够空间容纳旧程序和数据库文件。

版本限定为三段十进制数字 `MAJOR.MINOR.PATCH`。比较时逐段按数值比较，不进行
字符串排序，确保 `0.10.0 > 0.2.0`。同版本和降级都返回 `precheck_failed`。

## 6. 备份结构与提交

只保留最近一次升级前备份：

```text
/userdata/edgevision-gateway/upgrade-backup/
└── previous/
    ├── manifest
    ├── install/
    ├── systemd/
    ├── config/
    └── database/
```

备份先写入同级临时目录 `previous.new`。只有程序、unit、现场配置、数据库文件和
`manifest` 全部写入并验证后，才用同文件系统内的重命名替换 `previous`。
不在新备份完整前删除已有的可用备份。

`manifest` 至少记录：

- 原运行版本。
- 候选版本。
- 原安装目录、unit 和现场配置路径。
- 数据库主文件的精确路径。
- `.db`、`.db-wal`、`.db-shm` 各自是否存在、大小和 SHA-256。
- 备份完成标记。

现场配置加入备份，但正常升级不覆盖用户配置。若安装逻辑对配置执行了兼容迁移，
回滚时将其恢复到备份状态。

## 7. 数据库变化判断与恢复

旧服务停止后，数据库文件集合处于稳定状态。备份主 `.db` 文件，并在存在时同时备份
`.db-wal` 和 `.db-shm`。

候选健康检查失败后：

1. 先停止候选服务，保证不再写入。
2. 对当前 `.db`、`.db-wal`、`.db-shm` 记录存在性、大小和 SHA-256。
3. 与 `manifest` 中的备份状态比较。
4. 文件集合完全相同时，不覆盖数据库。
5. 任一文件新增、消失、大小改变或校验值改变时，恢复整套备份文件。

恢复不使用通配符。脚本从受验证的 `manifest` 读取主数据库精确路径，只处理该路径及
对应的 `-wal`、`-shm` 路径。需要恢复时，先将当前三个精确目标移入临时隔离目录，
再安装备份文件。恢复完成且旧服务验证通过后才清理隔离副本。

## 8. 回滚顺序

候选版本失败时严格按以下顺序执行：

1. 停止候选服务。
2. 比较当前数据库文件集合与备份。
3. 恢复旧程序、脚本、unit 和需要恢复的现场配置。
4. 仅在数据库发生变化时恢复数据库文件集合。
5. 执行 `systemctl daemon-reload`。
6. 启动旧服务。
7. 通过 `gatewayctl get_version` 查询实际运行版本，必须等于 `manifest` 中的原版本。
8. 运行旧版本健康检查。

若旧程序已恢复且运行版本正确，但串口等环境错误导致健康检查失败，脚本返回
`upgrade_failed_rollback_unhealthy`，不宣称回滚健康。

## 9. 返回结果

| 结果 | 含义 |
| --- | --- |
| `upgrade_committed` | 候选版本已启动，运行版本与候选版本一致，完整健康检查通过 |
| `precheck_failed` | 安全检查、版本格式或版本关系不满足；旧服务未停止 |
| `backup_failed_old_restored` | 备份未完成，候选版本未启动，原服务已恢复并验证健康 |
| `upgrade_failed_rollback_ok` | 候选版本失败，旧程序已恢复，数据库按需恢复，旧服务健康 |
| `upgrade_failed_rollback_unhealthy` | 旧程序和相应数据库已恢复，但旧服务仍因环境或外部依赖错误不健康 |
| `rollback_failed` | 程序、unit、配置、数据库或服务恢复过程本身失败，需要人工处理 |

上述结果均输出为稳定、可检索的结果行。除 `upgrade_committed` 外均返回非零退出码。

## 10. 故障处理原则

- 任何状态转换失败都保留原始诊断输出。
- 启动成功不等于提交成功；必须查询运行版本并通过完整健康检查。
- 串口、GPIO、MQTT 等环境错误可能同时影响新旧版本；回滚脚本必须如实报告。
- 发生 `rollback_failed` 时不自动尝试更多破坏性操作，保留备份、隔离副本和日志供人工处理。

## 11. 验证策略

用临时目录和可控的假 `systemctl`、`gateway`、`gatewayctl`、`sqlite3` 驱动真实升级脚本。
至少覆盖：

1. 安全检查通过，高版本候选服务健康，提交成功。
2. 同版本、降级、非法版本格式和发布包校验失败均不停止旧服务。
3. 旧服务或数据库在升级前已不健康时拒绝升级。
4. 程序备份、数据库备份、元数据写入或备份提交失败时，不启动候选版本。
5. 候选健康失败且数据库文件集合未变时，只恢复程序。
6. 主 `.db`、`-wal` 或 `-shm` 任一发生变化时，恢复完整备份集合。
7. 回滚后实际运行版本必须等于备份版本。
8. 串口不存在等环境错误导致旧版本不健康时，返回 `upgrade_failed_rollback_unhealthy`。
9. 旧程序、数据库或服务恢复失败时，返回 `rollback_failed` 并保留现场证据。
10. 第二次升级只在新备份完整后替换 `previous`，不保留多代备份。

Shell 脚本必须通过 POSIX `sh -n`和 BusyBox `sh -n`。涉及文件替换的测试还要断言最终
程序内容、数据库文件集合、服务调用顺序和结果行，不只检查退出码。
