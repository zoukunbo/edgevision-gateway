## 1. 当前实际测试链路

```text
PC 串口助手 COM9
  -> USB TO RS485 (C) 的 A+/B-
  -> 3485/485 模块的 A/B
  -> 模块 RO -> P16 Pin10 (UART5_RX)
  <- 模块 DI <- P16 Pin8  (UART5_TX)
     模块 RSE <- P16 Pin7 (GPIO0_C6，gpiochip0 offset22)
     模块 VCC <- 板上3.3V；模块 GND <-> 板上 GND
```

USB-RS485 的 GND 在照片中接有橙线；最终对应的板端 GND 引脚需现场确认。
不能根据颜色判断线序，也不能把 A/B 差分线直接接 UART 的 TX/RX。
上图是根据现有资料整理的目标映射，不替代断电后的逐线核对。
当前没有收到真实 Modbus 传感器/仪表型号及手册。

## 3. 已有原始字节证据（不是20组设备事务）

下面是从用户截图转录的已验证内容；无原始时间戳，不编造次数。

```text
方向：开发板 -> PC
TX bytes: 11 22 33 44 55
PC HEX receive: 11 22 33 44 55

方向：PC -> 开发板
PC HEX send: 01 03 00 00 00 02 C4 0B
Board output:
RS485 initialized: /dev/ttyS5, RSE=RX
RS485 TX complete
Waiting for RX data, timeout=10s...
RS485 RX 8 bytes: 01 03 00 00 00 02 C4 0B
```

第二组8字节是 PC 发来的读寄存器请求样式，不是从站读寄存器响应；
开发板 demo 也没有实现 Modbus 从站。因此不能把它计作真实设备事务成功。

缺少：真实从站的20组请求和对应响应。取得设备资料后，保存序号、时间、
TX HEX、RX HEX、耗时和结果；超时/异常也如实保留，不能复制成功样本补数。
当前 demo 的五字节测试串不能用作真实仪表查询。

## 5. 已知故障与定位顺序

已发生的故障：上电后未配置串口，补充 stty/termios 后收发正常。
这是参数初始化遗漏，不把它改写成做过“故意错波特率/反接A/B”的实验。

定位顺序：先断电核对供电和线序，再查共地/电平与GPIO方向，再查串口参数、
实际字节、协议参数，最后核对部署产物。不要为凑故障项随意带电改线。
D36原文要求错波特率或A/B反接现象之一；当前只能记录已发生的参数故障，
若需严格逐项验收，该特定故障项仍需确认，不能伪造。

使用和部署见 [开发指南](../../docs/rs485-uart5-nfs-development-guide.md)。
